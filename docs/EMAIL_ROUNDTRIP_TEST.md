# Step 1: Email round-trip test

Proves Q2 of the POC spec — Salesforce can send an email to an external mailbox
and see the reply — before any Google or Gemini work starts.

Target org: `dev5-ts` sandbox (`wchaipitch@terrasky.co.th.dev5`).
Note that `CLAUDE.md` names a `booking-poc` sandbox; that org does not exist yet,
so the POC currently lives in `dev5-ts` alongside the leave-management work.

## What was deployed

| Component | Purpose |
|---|---|
| `Inbound_Email_Log__c` | Raw capture of every message the Email Service receives: from, to, subject, both bodies, all headers, `Message-ID`, `In-Reply-To`, parsed `[Ref:AR-nnnnn]`, auto-reply flag |
| `BookingInboundEmailHandler` | `Messaging.InboundEmailHandler`. Writes one log record per message. Never throws — an exception out of an Email Service bounces the sender's mail |
| `BookingPocReplyService` | The Email Service, local part `bookingpoc`, run-as `wchaipitch@terrasky.co.th.dev5`, accepts mail from anyone |
| `BookingEmailTester` | Anonymous-Apex helper that sends one test email with Reply-To set to the service address |
| `Booking_POC_Admin` | Permission set granting object and field access. **Required** — without it the fields are invisible even to a System Administrator |
| Tests | `BookingInboundEmailHandlerTest`, `BookingEmailTesterTest` |

## One-time org setup

1. **Email deliverability must be `All email`.**
   Setup → Email → Deliverability → Access level. A sandbox refresh resets this
   to `System email only`, which silently drops outbound mail — Apex still
   reports success.
2. **Copy the Email Service address.**
   Setup → Email → Email Services → `BookingPocReplyService` → the email address
   row. It looks like `bookingpoc@<hash>.<sandbox>.apex.sandbox.salesforce.com`.
   This value is generated by the org and is not in the metadata, so it has to
   be read from the UI once.
3. Assign `Booking_POC_Admin` to anyone who needs to read the logs:
   `sf org assign permset --target-org dev5-ts -n Booking_POC_Admin -b <username>`

## Running the test

Send, substituting the address from step 2:

```bash
sf apex run --target-org dev5-ts <<'APEX'
System.debug(BookingEmailTester.sendTestEmail(
    'chaipitch6@gmail.com',
    'bookingpoc@<hash>.<sandbox>.apex.sandbox.salesforce.com'
));
APEX
```

The mail arrives from the running user's own address
(`wchaipitch@terrasky.co.th`) with subject
`Booking POC round-trip test [Ref:AR-00001]`.

Reply from Gmail with any text, keeping the subject line, then check what came
back:

```bash
sf data query --target-org dev5-ts -r human -q "
  SELECT Name, Received_At__c, From_Address__c, To_Address__c, Subject__c,
         Reference_Code__c, Is_Auto_Reply__c, Body_Plain__c
  FROM Inbound_Email_Log__c ORDER BY Received_At__c DESC LIMIT 5"
```

## Pass criteria

- The email reaches the external mailbox.
- The reply creates one `Inbound_Email_Log__c` record within a minute or so.
- `Reference_Code__c` is `AR-00001` — the subject token survives Gmail's
  `Re:` prefix, which is what the real reply matching will rely on.
- `Body_Plain__c` contains the reply text plus Gmail's quoted history. Stripping
  that history is `ReplyCleaner`'s job, later.

## If no record appears

- Check the Email Service is active and its address is active.
- Setup → Email Services → the service → **Failure Response Settings**; a
  bounced message means the handler threw or the address was rejected.
- Check Apex debug logs for the run-as user — the handler logs capture failures
  at ERROR level rather than throwing.
- Confirm the reply really went to the service address, not to the sender's
  address: Gmail replies to `Reply-To` only if the header was set.
